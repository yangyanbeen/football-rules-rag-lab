# 足球规则 RAG 中文语料与检索系统技术文档

版本：1.0  
记录日期：2026-11-10  
项目状态：中文语料构建已完成；RAG 应用、检索实验和问答评测尚未完成。

## 1. 项目概述

本项目为足球规则问答准备可追溯的中文资料，并计划在成熟的开源文档问答应用上实现检索优化。系统最终应能根据中文问题找到支持答案的规则段落，给出简明回答、规则条目和来源链接；证据不足或问题超出资料范围时，应说明无法从当前资料确认。

当前交付包含 18 个英文 Wikipedia 来源页的网页文本快照、5 份中文规则资料、99 个结构化知识段、英中对照 JSONL、HTML 阅读页、来源清单和语料校验报告。规则相关正文译文共 20,601 个字符，其中汉字 18,000 个；对应的英文摘录共 87,419 个字符。字符数不等于模型 token 数。

目前完成的是**语料采集快照、整理、翻译、切分和结构校验**。Kotaemon 尚未在此项目目录中完成安装与运行；向量索引、BM25、RRF、BGE-Reranker、FAISS HNSW、Redis 缓存、LangGraph 流程和离线检索评测均属于后续方案，不能描述为已经实现或已经取得性能收益。

## 2. 项目目标与边界

### 2.1 目标

- 让每个中文知识段能追溯到来源页、可见修订号、原文行范围和内容校验值。
- 保留规则标题、条件、例外和表格，使切分后的段落能独立检索并正确引用。
- 在固定数据和评测集上比较基线、混合召回、重排及结构切分方案。
- 记录配置、代码版本、数据版本、评测集版本、运行环境和原始结果，让简历中的数字可复核。

### 2.2 当前不覆盖

- 这批 Wikipedia 资料是社区维护的二手概述，不是 IFAB 官方规则原文，也不是某一赛季完整规则书。
- 当前中文内容是 AI 翻译并经编辑整理的阅读版，未经过裁判专家审校。
- 目前没有已测得的 Recall、MRR、nDCG、答案准确率、引用命中率、并发量或延迟优化结果。
- 项目不训练基础大模型、不获取实时比分，也不以增加 Agent 数量作为项目目标。

## 3. 现有语料构建流程

```text
Wikipedia 规则总览及规则专题页
        ↓ 网页读取通道取得带行号的文本快照
data/raw/wikipedia_2026-11-10/
        ↓ scripts/build_rules_document.py
英文清洗文档、来源元数据、来源 CSV 和 SHA-256
        ↓ scripts/build_chinese_rules.py
5 份中文分卷、HTML 阅读页、中文 JSONL、英中对照、语料 manifest
        ↓ 结构与文件一致性检查
validation_report.json 和语料 ZIP
        ↓ 后续待做
RAG 导入、检索基线、逐项优化与离线评测
```

### 3.1 来源采集与版本记录

来源页来自英文 Wikipedia 主条目及其直接链接的足球规则专题页，白名单限定为 18 页。抓取内容仅用于规则相关文本整理，不递归遍历整站，也不收集图片或媒体。

本轮本机直连 Wikimedia API 超时，故通过网页读取通道保存带行号的文本快照；这些文件不是网站原始 HTML，也不是 API 原始 JSON。18 页均记录了页面可见的页脚 revision ID，但指定历史版本正文未能逐页重新获取并独立核验。因此，revision ID 只表示读取快照中显示的版本编号；本次实际语料由本地快照和 SHA-256 固定。不要把该记录写成“已从 API 验证全部历史版本”。

来源及许可信息包括页面标题、URL、语言、revision ID、获取方式、快照文件、SHA-256、署名和 CC BY-SA 4.0 链接。Wikipedia 是二手资料，可能过时、缺漏或存在错误。公开分发改编语料时须遵守适用的署名和相同方式共享要求，并将代码许可证与语料许可证分开说明。

### 3.2 清洗与英文快照

`scripts/build_rules_document.py` 离线读取 `data/raw/wikipedia_2026-11-10/` 中的快照，按行号合并重叠片段，去除读取界面的导航和链接标记，依规则范围保留正文，并生成英文 Markdown、HTML、来源 JSON/JSONL、摘要和 `data/manifests/sources.csv`。脚本使用已有本地快照，不负责联网抓取。

当前英文清洗正文为 146,474 个字符。正文包含规则相关内容和部分背景说明；它不是 146,474 字符全部翻译为中文的文本。

### 3.3 翻译与中文分卷

`scripts/build_chinese_rules.py` 根据人工整理的规则单元和英文快照生成中文 Markdown、HTML、JSONL、manifest、阅读入口与 ZIP。中文分为：

1. 场地、器材与队员
2. 裁判、比赛流程与结果
3. 越位、犯规与纪律
4. 任意球与罚球点球
5. 界外球、球门球与角球

共 99 个知识段，覆盖《竞赛规则》第 1—17 条的主要相关内容。译文对应 87,419 个英文原文摘录字符；非规则材料、部分历史、战术内容、图片说明及重复例子没有全部翻译。逐段保存来源行范围和原文/译文 SHA-256。28 段有明确校核提示，99 段均未经过裁判专家审校。

## 4. 结构化知识段设计

当前采用语义边界切分，不按固定字符数截断。每个三级标题对应一个主要知识单元，尽量把规则主体、适用条件、例外和相关解释放在同一段内；点球处理表保留为一个整体单元。中文知识段正文长度中位数为 203 个字符，最大为 425 个字符。这是字符统计，后续仍需使用实际 tokenizer 测量 token 数。

现有稳定编号沿用源规则主题，例如 `L11-03` 表示第 11 条下的一个知识段。稳定 ID 不应因重新排序而改变。若某个现有知识段需拆成多个检索子段，应为新子段建立明确的子 ID，并保留原 ID 作为 parent；不得静默重编号。

建议后续 RAG 数据在现有字段基础上补充父子结构和实际切分类型：

| 字段 | 用途 |
| --- | --- |
| `id` / `chunk_id` | 知识段稳定 ID；当前 JSONL 使用 `id` |
| `parent_id` | 父级规则单元或章节 ID；当前尚未生成 |
| `document_id` | 所属中文分卷，如 `football-zh-03` |
| `section_path` | 分卷、规则条目、知识段标题构成的标题路径 |
| `chunk_type` | 段落、定义、例外或表格；当前尚未显式提供此字段 |
| `text` / `content_zh` | 中文检索文本；当前 `chunks_zh.jsonl` 使用 `text` |
| `content_en` | 对应英文原文摘录；保存在英中对照 JSONL，而非中文检索 JSONL |
| `source_id`, `source_url` | 来源页 ID 和 URL |
| `source_revision_id`, `source_revision_status` | 可见版本编号及其核验边界 |
| `source_lines` | 来源快照行号范围 |
| `source_text_sha256`, `translated_body_sha256` | 原文摘录和中文段落校验值 |
| `translation_method`, `official_translation`, `expert_reviewed` | 翻译方式及审校状态 |
| `needs_rule_review`, `review_notes` | 规则核对标记和具体问题 |
| `license`, `license_url`, `source_attribution` | 再利用时的署名和许可信息 |

当前 `chunks_zh.jsonl` 的一行包含 `id`、`text`、`metadata`；`parallel_zh_en.jsonl` 包含 `id`、`title_zh`、`text_zh`、`text_en`、`metadata`。两份记录按 `id` 对齐。添加新字段时应更新生成脚本、文档、manifest 和导入适配器，并保持旧 ID 可映射。

## 5. 目标 RAG 架构

以下是待实现的目标数据流，参数均为待评测的起始方案，而不是已验证的最佳值：

```text
用户问题
   ↓
问题规范化与规则版本/主题识别
   ↓
稠密向量召回 ───────────────┐
BM25 中文词法召回 ──────────┤
   ↓                         ↓
按 chunk_id 去重并保留两路排名 → RRF 融合（起始 k=60）
                                  ↓
                         候选截断（如 Top-40）
                                  ↓
                         BGE-Reranker 重排
                                  ↓
                 子段命中，父段补上下文并保留出处
                                  ↓
         基于证据生成回答 → 检查引用与条件/例外 → 输出或拒答
```

### 5.1 稠密检索与 BM25

稠密检索将中文问题和知识段编码为向量，检索语义相近的段落；BM25 按词项匹配，适合规则编号、固定术语、数字和专有说法。中文 BM25 需要确定一致的分词/词典策略，可将 jieba 作为候选实现，但应在同一评测集上与其他分词设置比较。Embedding 模型、向量维度、归一化方式及距离度量尚未锁定。

每条召回结果应保留 `chunk_id`、原始排名、分数和检索通道。召回结果按稳定 ID 去重，便于复现和定位错误。

### 5.2 RRF 排名融合

对每路检索结果按排名融合，初始公式为：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

`d` 是知识段，`rank_i(d)` 是它在第 `i` 路中的名次；未出现于某路的段落对该路不计分。初始 `k=60`，应作为配置项保存。实验至少比较 BM25、dense、两路候选并集和 RRF，使用相同语料、测试问题及候选数。

### 5.3 Reranker 与父子块

融合后可将候选集截断到 Top-40，再由 BGE-Reranker 对问题与候选段落重新评分。Top-40 只是实验起点，应和 Top-20、Top-80 及不使用 reranker 的结果比较，分别记录 Recall/MRR/nDCG 与 rerank 延迟。

父子检索中，较小的子段用于命中问题，父段提供完整上下文。最终引用应指向原始来源页、规则标题和段落 ID。若父段由多个已有关联段落合成，需明确记录成员 ID，避免将无关内容拼成一个证据块。

### 5.4 索引、缓存与编排

- **向量存储：**Chroma 是带集合/持久化接口的向量数据库；FAISS 是向量相似搜索库。可先采用 Kotaemon 当前易接入的存储跑通基线，再决定是否单独实现 FAISS adapter。FAISS HNSW 的 `M`、`efConstruction`、`efSearch` 调优属于可选实验。
- **缓存：**Redis 可先用于查询结果缓存、限流或后续语义缓存。语义缓存必须评估错误命中、失效规则、跨版本隔离、命中延迟及调用节省，缓存命中率本身不能代表回答可靠。
- **编排：**LangGraph 可在需要显式分支、重试和状态追踪时编排问题路由、检索、版本识别、证据重排、答案生成、引用校验和最终输出。首个可运行版本建议先采用清晰、可观测的单条检索链；多 Agent 或多节点本身不是质量指标。
- **用户界面：**规划以 Cinnamon/kotaemon 作为文档问答底座。需固定上游 tag/commit，记录本地安装配置和修改边界；本项目当前尚未完成该底座的安装和启动。

## 6. 版本、评测与质量控制

### 6.1 数据版本

每次语料变化都应产生可区分的语料版本。至少记录：来源清单版本、原始快照 SHA-256、处理脚本 commit、中文文档/JSONL SHA-256、更新时间、许可信息和翻译/审校状态。重新获取页面时不要覆盖旧快照；新旧版本应能并存和比较。

当前页面元数据保存在 `data/manifests/wiki_collection_2026-11-10.json` 与 `data/manifests/sources.csv`，中文输出摘要和文档哈希保存在 `data/processed/wikipedia_zh_2026-11-10/corpus_manifest.json`。目前没有单独的 `page_manifest.jsonl`；如后续需要该格式，应从已有来源清单导出，不手工维护第二份容易漂移的数据。

### 6.2 当前已经检查的内容

现存 `validation_report.json` 为 PASS，检查项包括：99 个知识段 ID 唯一、第 1—17 条均有覆盖、英中记录可按 ID 对齐、文档 SHA-256 匹配、HTML 导航锚点有效、点球表格未拆散、CC BY-SA 提示存在、ZIP 完整性通过。此报告验证文件结构、来源追溯和包完整性，不证明译文准确或规则内容现行有效。

需要持续标记的来源/翻译风险包括：近似英制换算与正式公制尺寸可能不一致；坠球来源描述旧程序；部分赛事举例缺少赛季条件；个别处罚表简化了适用条件；部分规则例子可能省略上下文。相关段落带有 `needs_rule_review` 或 `review_notes`，需要专家或权威现行资料核对后才适合作为“现行规则”标准答案。

### 6.3 离线检索评测设计

先建立 30–50 条人工核对的问题集，验证评测脚本和数据标签，再扩充正式开发集与锁定测试集。问题应覆盖第 1—17 条、数字/术语、条件与例外、重新开始比赛方式、跨段问题、资料外问题和版本不明确问题。hard negative 应是主题相近但不支持答案的段落，并记录不相关原因。

| 指标 | 建议口径 | 当前状态 |
| --- | --- | --- |
| Recall@5 / Recall@10 | 可回答问题的正确证据至少一条进入前 K 的比例；记录样本数及证据标注规则 | 待测 |
| MRR@10 | 每题第一个正确证据名次倒数的均值，截断至前 10 | 待测 |
| nDCG@10 | 需要分级相关性标签；公开评分规则并固定标签 | 待测 |
| Precision@K | 前 K 个结果中相关证据所占比例 | 待测 |
| 引用正确率 | 引用是否实际支持答案中的规则结论；人工抽样复核 | 待测 |
| 版本识别准确率 | 对指定赛季/规则版本的识别是否正确 | 待测；目前语料不是单一官方赛季资料 |
| 条件/例外召回率 | 标注问题要求的条件和例外是否都进入证据或答案 | 待测 |
| 检索/重排延迟 | 分开记录检索、rerank 和端到端；统一预热、并发、次数，报告 P50/P95 | 待测 |
| 答案拒答质量 | 分开统计资料外问题正确拒答和可回答问题错误拒答 | 待测 |
| chunk 长度 | 明确 tokenizer，报告均值/中位数/P95、块数和切片数 | 目前只有字符统计 |

每次实验保存 Git commit、语料和评测集 hash、模型及版本、参数、硬件、运行时间、随机种子（如适用）、原始逐题结果和错误案例。所有模型或索引参数对比须使用相同锁定测试集；若测试集或标注变更，应升版本，不与旧结果直接混比。

### 6.4 实验推进顺序

1. 固定 Kotaemon 版本，跑通原始导入和引用流程。
2. 创建小型人工核对评测集，完成检索指标脚本和 baseline。
3. 分别测 dense 与 BM25，再测 hybrid 和 RRF。
4. 比较无 rerank 与不同候选截断范围的 reranker。
5. 引入结构切分和父子块，对照当前 99 个语义块。
6. 只有基线稳定后，再开展 HNSW 或缓存实验。

每一步只改变一个主要因素，并在 `docs/EXPERIMENT_LOG.md` 记录假设、验收条件、数据版本、结果和去留结论。无实验数据时写“待测”，不得补造简历数字。

> 整理足球规则相关英文网页快照，构建 5 份中文主题资料和 99 个带来源页、修订编号、原文行范围及校核状态的结构化知识段；生成英中对照 JSONL、文档哈希和离线校验报告，为后续 RAG 检索评测准备可追溯语料。
