# 开发工作流（新手版）

## 一次只做一个可验收的小目标

每项工作按以下顺序执行，完成后才能进入下一项：

1. **描述问题**：用户哪里不方便，或评测中哪项指标暴露问题？
2. **写验收条件**：例如“正确规则段落 Recall@5 高于当前 baseline，且检索 P95 不增加超过 20%”。阈值按实验目标制定，不默认套用这个例子。
3. **记基线**：代码 commit、规则资料版本、评测集版本、模型、参数、硬件和当前结果。
4. **建分支**：每个功能/实验一个分支，避免混合多个原因。
5. **最小改动**：仅实现当前假设所需的部分。不要顺手重构无关代码。
6. **验证与记录**：跑对应检查，保存原始结果、失败案例和运行方式。
7. **作决定**：通过则合并；无收益或有明显副作用则撤销或保留实验分支，不进入主线。
8. **更新文档**：更新 EXPERIMENT_LOG；若架构/范围/数据口径变了，也更新对应权威文档。

## 文档更新判定

| 变化 | 必须更新 |
| --- | --- |
| 项目用户目标、范围、优先级改变 | `PROJECT_SCOPE.md`、README |
| 新组件/存储/模型边界或技术取舍 | `DECISIONS.md`、架构图（如已有）、README 摘要 |
| 新数据源、版本、清洗、标注规则或许可状态变化 | `DATASET.md`、`sources.csv` |
| 新实验、指标数字、消融结果、失败结论 | `EXPERIMENT_LOG.md` |
| 安装、运行或用户操作变化 | README 的运行指南或单独 `docs/LOCAL_SETUP.md` |
| 仅变量名/注释/内部小修，不影响上述内容 | 写清楚提交说明即可，无需改专题文档 |

文档是代码和项目事实的记录，不写空洞承诺。未做完的任务用 checkbox，完成后留下日期/commit/结果。

## Git 建议

- `main` 始终尽量保持可运行。
- 分支例：`feature/eval-baseline`、`feature/rrf-fusion`、`experiment/chunk-size`。
- 一次提交围绕一个目的。提交前看改动范围，确认未带入 `.env`、`data/raw/`、模型缓存或临时大文件。
- 开始公开同步前，确认上游许可证、语料再发布权限、密钥、个人信息。
- 重要实验结果和代码 commit 互相引用，避免只留在聊天记录里。

