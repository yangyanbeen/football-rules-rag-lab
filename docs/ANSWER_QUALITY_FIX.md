## 2. 已确认的原因

1. **上下文被服务端截断。** `reports/ollama-server-2026-11-11.log` 明确出现 `truncating input prompt`，例如 prompt=5869/6114/6441、limit=2050。上游应用准备的大量证据与旧会话内容无法完整送达模型。
2. **问答与引用分开生成。** 上游 CitationPipeline 独立做工具调用；实际日志多次 `Got 0 cited docs`。答案中的段落号由模型写出，没有与最终展示的证据建立确定绑定。
3. **临时块混合规则。** UI 的 50 个应用块包含多个知识段；球门球证据与任意球、角球等相似内容混在候选中。对稳定 99 单元做只读定位时，球门球 L16-03 在全库 Dense 候选中排第 9，不能靠少量粗块或默认生成保证正确使用。
4. **同主题不等于支持。** 第一轮只核对回答非空、引用 ID 存在，仍出现 Q2 混入间接任意球、Q3 引用角球。后续加入支持段/禁用错段约束后才判定质量是否通过，未将第一轮结构 PASS 当成质量通过。

## 3. 当前实现

```text
现有用户所选文件检索
  → 核对文件名和原文 SHA-256，确认可使用的冻结文档范围
  → 从原 99 个稳定单元读取正文及 metadata（不覆盖输入）
  → 识别明确的规则主题，区分判罚行为与执行程序
  → bge-m3 cosine 排名，最多 20 候选；明确主题每条规则最多 4 段
  → 在 token 预算内保留整知识段，超预算不截断半段
  → 本地 qwen2.5:3b 仅选择已有 chunk ID；比较题补查缺少的规则证据
  → 程序校验所选 ID，仅从冻结语料读取完整自然段
  → 完整知识段摘录 + 程序生成的 chunk ID/规则号/源行/URL
  → 将校验后的整条回答交给 UI，右侧显示同一批证据
```

**采用保守的摘录式回答。** 模型不生成供用户阅读的规则正文、引用号或 URL；正文从选中的原知识段逐段复制，恢复该段所有相邻自然段，保留条件、例外、表格和校核提示。因此有些回答会比原先更长，也可能带有额外相关背景。它不保证任意未见问题都能选中最精简、最相关的证据。

范围控制沿用上游所选文件检索结果，再验证实际文件哈希；没有有效文件、模型输出不合法、证据不足、问题过长或模型不可用时不给出无证据规则结论。历史错误回答不再加入当前规则证据。

本轮 Dense 向量是 `.cache/football-quality/` 中按语料哈希、检索文本模板和 Embedding digest 隔离的本地运行缓存；未建立任务 5 的正式发布索引，未把它冒充 RAG B0、Retrieval B0 或正式评测成果。既有 50 块应用索引仍保留。
