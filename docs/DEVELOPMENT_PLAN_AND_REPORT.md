# 足球规则 RAG 知识库完整开发计划与阶段报告

版本：2.0  
报告日期：2026-11-10  
依据：`docs/TECHNICAL_DESIGN.md`、项目现有文件及用户提供的任务拆解提示词

## 1. 审核结论

上一版可以作为“检索优化任务提纲”，但还不足以当作从已有语料构建完整 RAG 知识库的执行计划。主要缺口是：

- 把重心放在 Dense、BM25、RRF、Reranker 等检索优化上，没把数据导入、索引构建、回答生成、引用展示、拒答、应用打包串成一条完整可运行流程。
- 逐项交付物和验收条件偏概括，难以判断一个阶段是否真的完成、能否交给下一阶段。
- 没有把已经存在的 5 份中文文档与 99 个知识段明确规定为基线输入，容易让人误以为还要重新生成语料。

本版以现有语料为固定起点，补齐从数据审计到本地可运行问答系统、离线评测和交付的主线。每项任务都写明输入基线、交付物和最低通过条件。下文的“交付基线”指**进入下一项前必须提交并通过的最小成果**，不代表预设的性能数字。

### 2.2 当前进度

任务 1 语料审计/冻结和任务 2 Kotaemon 固定版本/本机运行冒烟已完成。任务 2 用五份 Markdown 在 Kotaemon UI 建立了 50 个临时应用 chunk，并记录了三条原始回答；它没有导入 Corpus B0 的 99 个稳定知识段，也没有建立正式 RAG B0。稳定语料导入适配器、评测集、正式索引、BM25、检索与答案评测、引用校验和交付打包仍待任务 3—14 完成。当前没有 Recall、MRR、nDCG、正式引用正确率或受控延迟数据。项目根目录没有 Git 元数据；不初始化 Git，使用文件清单、SHA-256 和实验日志追踪。

| 名称 | 含义 |
| --- | --- |

| **RAG B0** | 首次完整导入 Corpus B0 后，由固定应用、Embedding、向量存储和默认检索配置组成的可运行问答基线。任务 2 的 UI 冒烟只导入了五份 Markdown 并临时切出 50 个 chunk，**不算 RAG B0**；当前尚未建立。 |

## 3. 完整知识库构建流程

```text
已有 5 份中文文档 + 99 个知识段（Corpus B0，已完成）
        ↓ 任务 1：审计、校验、冻结输入和文件哈希
固定数据版本与来源映射
        ↓ 任务 2：固定 Kotaemon 版本并验证运行环境
        ↓ 任务 3：定义统一数据结构并导入现有知识段
        ↓ 任务 4：建立人工开发集和锁定测试集
        ↓ 任务 5：选定 Embedding / 向量存储并构建索引
        ↓ 任务 6：接入检索、LLM、提示词、引用和拒答
完整可运行 RAG B0
        ↓ 任务 7–11：建立检索基线并逐项优化
        ↓ 任务 12：评测答案、引用、条件/例外和拒答
        ↓ 任务 13：打包、复现说明、演示和回归检查
        ↓ 任务 14：归档实验与简历证据

可选增强（核心链路通过后）：FAISS HNSW、Redis、LangGraph
```

这里将现有 JSONL 作为知识段导入的优先数据源，以保留每段稳定 ID 和来源行号。直接把 5 份 Markdown 上传到应用也可用于任务 2 的界面冒烟验证，但如果应用自行重新切分，产生的临时 chunk 不得替代 Corpus B0，也不能用来计算正式基线。

## 4. 执行顺序与分阶段报告

### 阶段 A：固定语料与环境

#### 任务 1：项目现状审计与语料冻结

**输入基线：**现有 5 份 Markdown、99 条中文 JSONL、英中对照 JSONL、语料 manifest、validation report、来源清单和处理脚本。

**工作内容：**核对文件是否齐全；统计来源页、文档、知识段和 JSONL 行数；检查重复 ID、空正文、缺来源 URL/行号、英中 ID 对齐及校验值；记录 Python、依赖、模型缓存、向量库、Kotaemon 和 Git 状态。发现问题先记录，不在这一步编辑 5 份中文文档。

**交付基线：**

- `docs/PROJECT_AUDIT.md`：区分已完成、待实现、异常和风险。
- `data/manifests/project_file_manifest.json`：至少记录相对路径、字节数、SHA-256、文件用途；原始数据按既有许可/忽略规则处理。
- 更新 `docs/EXPERIMENT_LOG.md`：记录本次审计日期、命令和结果。

**通过条件：**审计数量与 Corpus B0 对得上；99 条知识段可唯一定位且能回溯来源；环境结论有实际命令输出或明确标记未检查；没有修改原有 5 份文档。Git 不存在时如实记录，不执行 Git 初始化。

#### 任务 2：固定上游版本并建立可运行应用

**输入基线：**任务 1 通过；Cinnamon/kotaemon 上游仓库和官方安装说明。

**工作内容：**选定并记录可复现的 tag/commit；按其要求建立隔离环境；记录 Python 与关键依赖；用现有中文资料完成 UI/服务启动和小规模冒烟提问。此处先验证应用能运行，不将应用自带切分结果当作正式知识索引。

**交付基线：**

- `docs/UPSTREAM_VERSION.md`：仓库 URL、tag/commit、许可证、安装来源和固定日期。
- `docs/LOCAL_SETUP.md`：环境准备、启动、关闭、常见错误；只放 `.env.example`，不得提交真实密钥。
- `scripts/run_baseline_check.ps1` 或等价启动脚本，以及不含密钥的运行日志/截图。
- `docs/KOTAEMON_BASELINE.md`：记录当前默认 Embedding、存储、分块、Top-K、LLM 和引用行为；未知项标“待核对”。

**通过条件：**能按文档启动；至少 3 个中文问题能得到结果；运行日志或截图能证明实际运行；若被依赖、模型下载或硬件阻塞，记录确切错误和可复现步骤，不声称已经跑通。

### 阶段 B：数据接入与评测基线

#### 任务 3：定义统一数据结构并适配现有语料

**输入基线：**Corpus B0 和任务 1 的审计结果。已有 `chunks_zh.jsonl` 的字段是 `id/text/metadata`；英中对照数据是 `id/title_zh/text_zh/text_en/metadata`。现有数据没有显式 `parent_id` 或完整的 `chunk_type`。

**工作内容：**按 ID 合并中文与英文记录；规范来源、版本、行号、许可、翻译状态、校核提示和哈希字段。当前没有可靠父块关系的记录将 `parent_id` 留空或标为根块，不推断虚构关系。能确定是表格的记录再标记 table 类型；无法判断的类型标 unknown。

**交付基线：**

- `docs/RAG_DATA_SCHEMA.md`：字段定义、允许空值、稳定 ID 和版本升级规则。
- `scripts/build_rag_dataset.py`、`scripts/validate_rag_dataset.py`。
- `data/processed/rag_chunks_zh.jsonl`、`rag_chunks_parallel.jsonl`。
- 校验结果保存为机器可读 JSON，并给出摘要。

**通过条件：**99 个旧 ID 均可映射；源 ID 不变；中文与英文记录按 ID 对齐；每条中文记录有 `source_url` 和有效 `source_lines`；来源修订状态保留原来的核验边界；输入原文件不被覆盖。

#### 任务 4：构建人工检索和答案评测集

**输入基线：**任务 3 的稳定 chunk ID、规则条目和来源路径。

**工作内容：**先做小型人工核对集验证数据格式和指标脚本，再形成开发集与锁定测试集。覆盖规则 1—17、术语/数字、条件与例外、跨段问题、难负例、资料外问题及版本不明确问题。hard negative 必须主题相似但确实不支持目标答案，并记录原因。

**交付基线：**

- `data/eval/retrieval_dev.jsonl`、`retrieval_test.jsonl`、`answer_eval.jsonl`。
- `docs/EVAL_DATASET.md`：标注准则、版本、样本数、切分方式、测试集冻结规则和人工复核记录。
- `scripts/validate_eval_dataset.py`：检查字段、ID、标签和来源引用。

**建议样本基线：**先制作 30–50 条开发题验证流程；第一版正式对比集建议至少 50 条锁定测试题，资源允许时扩到 100–200 条总问题。样本数是计划建议，不是现有成绩。测试题一旦用于正式比较即冻结；调参只看开发集。每题标注 `question_id`、`question`、`expected_chunk_ids`、`answerable`、`topic`、`difficulty`、`required_conditions`、`must_refuse`，难负例另存 ID 和理由。

**通过条件：**所有可回答题都指向至少一个人工核对的支持 chunk；不可回答题有拒答理由；问题覆盖和样本数有报告；hard negative 逐条有理由；脚本校验通过；锁定测试集在参数选择期间不被查看/用于调参。

#### 任务 5：选定 Embedding 并构建可追溯的向量索引

**输入基线：**统一 JSONL、开发/锁定测试集、任务 2 固定的应用版本。

**工作内容：**按实际 CPU/GPU、内存和安装条件选择 Embedding 与向量存储；固定模型 ID/revision、维度、文本模板、归一化和距离度量。先用 `content_zh` 加标题路径构造检索文本；保存向量索引和 ID 映射。开始不混入 BM25、RRF、reranker 或缓存。

**交付基线：**

- `scripts/build_dense_index.py` 和可重复读取/查询的索引适配层。
- `data/indexes/dense/`（索引、ID 映射和索引 manifest；大文件按仓库规则处理）。
- `docs/EMBEDDING_AND_INDEX.md`：模型、版本、设备、文本模板、维度、归一化、距离度量和重建方式。
- 一份小规模索引 smoke log；正式 Recall/MRR 指标留到任务 7。

**通过条件：**索引记录数和 ID 映射可核对到 99 个原始知识段；能从空索引按文档重建；给定 query 能返回稳定 ID、分数和来源 metadata；记录运行时间和环境。该步骤只验收索引可用，不提前发布检索效果指标。

#### 任务 6：打通端到端 RAG B0

**输入基线：**固定上游应用、统一语料数据、可运行的 Dense 索引、LLM 提供方配置。

**工作内容：**接入查询规范化、检索 Top-K、证据组装、LLM 答案生成、引用呈现和证据不足时的拒答。提示词要求只依据检索证据回答，保留规则条件/例外，明确展示来源链接、chunk ID、规则号和校核状态。模型密钥只通过环境配置，不写入代码或报告。

**交付基线：**

- 可启动的 RAG 问答链路和配置文件（无密钥）。
- `docs/RAG_B0.md`：Embedding、LLM、Top-K、提示词版本、存储、引用格式和运行方法。
- `reports/rag_b0_smoke.jsonl`：至少 3 条可回答问题及 1 条资料外问题的输入、证据、回答和引用。

**通过条件：**从查询到答案完整运行；可回答问题能显示真实检索来源；资料外问题能触发预期拒答/不确定回答；日志可区分检索结果和生成回答；任一回答都能回链至 chunk 和来源页面。该 smoke test 只证明链路工作，不代表答案准确率。

### 阶段 C：逐项检索优化

#### 任务 7：测量 Dense Retrieval B0

**输入基线：**任务 5 的 Dense 索引、任务 4 的锁定评测集。

**交付基线：**逐题预测、汇总指标、数据与模型 manifest、错误分析，以及 `docs/DENSE_RETRIEVAL.md` 中的最终测量口径。

**通过条件：**可回答/不可回答样本数量明示；Recall@5、Recall@10、MRR@10 和延迟可以从原始逐题结果复算；只在开发集上调试，锁定测试集只用于报告。

#### 任务 8：建立 BM25 中文检索基线

**输入基线：**同一语料、同一评测集和 Dense 记录。

**工作内容：**确定并固定中文分词方案（jieba 可作为候选）、版本、自定义词表、停用词和规则编号/数字保留策略；对比正文、标题+正文、标题路径+正文等检索文本模板。

**交付基线：**`scripts/build_bm25_index.py`、`scripts/run_bm25_retrieval.py`、BM25 索引、`reports/bm25_baseline.json`、逐题预测和 `docs/BM25_RETRIEVAL.md`。

**通过条件：**分词及词典设置可复现；同一评测集上输出 Recall@5/10、MRR@10 和 P50/P95；逐题结果保存排名和分数；报告规则编号、数字和专业术语的典型命中/漏召回案例。

#### 任务 9：实现混合召回与 RRF

**输入基线：**任务 7 Dense 结果与任务 8 BM25 结果。

**工作内容：**保留两路原始排名、分数和耗时；按 chunk ID 去重；比较 Dense、BM25、候选并集和 RRF。融合公式 `RRF(d)=Σ 1/(k+rank_i(d))`，默认 `k=60`，但设为可配置实验参数。

**交付基线：**RRF 模块、统一运行脚本、`reports/hybrid_rrf_results.json`、逐题双路排名和融合排名、错误分析及 `docs/RRF_EXPERIMENT.md`。

**通过条件：**排名来源可追溯；同一数据、测试集和候选规模下可复算融合结果；报告 Recall@5/10、MRR@10，有分级标签时再报告 nDCG@10；明确写出结果是优于、持平还是劣于单路，不预设提升。

#### 任务 10：接入 BGE-Reranker 并测试候选截断

**输入基线：**任务 9 中确定的 Dense/BM25/RRF 配置及同一锁定测试集。

**工作内容：**对比不重排与 Top-20、Top-40、Top-80 候选后重排；记录模型版本、设备、batch size、预热、候选生成和计时区间；分析截断丢失的正确证据。

**交付基线：**`scripts/run_reranker_experiment.py`、`reports/reranker_results.json`、前后排名逐题结果、错误案例和 `docs/RERANKER_EXPERIMENT.md`。

**通过条件：**同时报告 Recall@5/10、MRR@10、适用时的 nDCG@10、Rerank P50/P95 和总检索链路 P50/P95；Top-40 仅是候选实验，不能事先写成最优。

#### 任务 11：比较结构感知切分与父子块检索

**输入基线：**Corpus B0 的 99 个知识段和任务 4 的评测集。现有段落已经按规则标题/自然单元组织，故这是新实验，不是重新生成原始 5 份文档。

**工作内容：**只有超长单元才按 tokenizer 次级切分；保留标题路径、规则号、表格表头、条件和例外；生成独立的 parent/child 数据集。原 ID 保持可追溯，新 ID 有稳定映射，旧 Corpus B0 只读保留。

**交付基线：**`scripts/structure_aware_chunking.py`、独立的 `rag_chunks_parent_child.jsonl`、父子 ID 映射、`reports/chunking_comparison.json`、错误分析和 `docs/CHUNKING_STRATEGY.md`。

**通过条件：**明确 tokenization 模型与版本；提供字符数和 token 数分布；抽查条件/例外与表格完整性；同测试集比较 chunk 数、长度均值/中位数/P95、Recall@5、MRR@10、重复率和上下文冗余率。长度变短不能直接宣称冗余下降。

### 阶段 D：回答质量与可交付版本

#### 任务 12：评测回答、引用和拒答

**输入基线：**可运行 RAG B0 及优化后的最佳检索配置；任务 4 的答案评测标签。

**工作内容：**答案限制在证据范围内；验证引用是否支持答案，检查规则编号、条件、例外、版本和校核提示；处理无答案、来源冲突、版本不明和相似但不支持的情况。

**交付基线：**答案评测脚本、`reports/answer_quality_results.json`、逐题答案与引用、错误分析、`docs/ANSWER_EVALUATION.md`。

**通过条件：**报告答案要点覆盖率、引用正确率、条件/例外保留率、正确拒答率和错误拒答率；写明样本数、模型配置和人工判定方法；不得用语言流畅度代替事实准确性。

#### 任务 13：集成、复现和交付

**输入基线：**任务 1—12 中通过验收的内容。
